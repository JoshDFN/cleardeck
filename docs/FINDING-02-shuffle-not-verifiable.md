# FINDING 02 — CRITICAL: the provably-fair shuffle cannot be verified by anyone

**Status:** confirmed by reading the canister's own memory, 2026-08-04
**Severity:** CRITICAL to the product's central claim. Not a fairness defect — the deal is
still uniformly random — but the headline "anyone can verify" property is false, and every
honest third-party verifier will conclude that ClearDeck cheated.

## The one-line cause

`src/table_canister/src/lib.rs:2314`

```rust
let j = (random_value as usize) % (i + 1);
```

`random_value` is a `u64`. `usize` is **32 bits on `wasm32-unknown-unknown`**. So on-chain
this silently truncates to the low 32 bits. Compiled natively — which is where every
reimplementation, every unit test and every reader's mental model lives — `usize` is 64
bits and no truncation happens. The same source produces two different shuffles.

## Proof

A copy of the canister was instrumented with a probe query returning its live `deck`, its
in-memory `CURRENT_SEED` and its committed `seed_hash`, then a hand was dealt:

```
canister deck[0:4]   = 7c, 2d, 4d, Qd        (alice got 7c 2d, bob got 4d Qd)
CURRENT_SEED         = c480370703f1c886…eb6e66
committed seed_hash  = 2485930e5df18467…dcc6ba

SHA256(CURRENT_SEED) == committed seed_hash            -> TRUE   (commit-reveal is sound)
shuffle(seed) with 64-bit usize == canister deck       -> FALSE  (4s, As, 4h, 2s)
shuffle(seed) with 32-bit usize == canister deck       -> TRUE   (all 52 cards)
```

Everything else was eliminated first, which is why the cause is certain:

- The deployed wasm is byte-for-byte reproducible from source. A local rebuild of `ceacc37`
  through the exact `icp` recipe steps produced
  `0x13c0981ff8d2582439bb4530405e314c7a1860866cbae8733b235d04a7c247b2`, identical to the
  deployed module hash. So the source being read *is* the code running.
- The published algorithm is the real algorithm. `shuffle_deck` and `create_deck` were
  compiled from the actual `lib.rs` and called directly from an in-crate test; their output
  matched an independent Python reimplementation exactly.
- Dealing order is as documented: `deck[0..2]` to seat 0, `deck[2..4]` to seat 1, then
  burn / flop / burn / turn / burn / river. Confirmed against the probe's live deck.

## Why this matters more than it looks

1. **Every honest verifier concludes we cheated.** A player who does exactly what the
   README tells them to do — reimplement Fisher-Yates with the SHA-256 chain and replay the
   revealed seed — gets a completely different deck from the one they were dealt. The
   natural conclusion is not "subtle integer-width bug", it is "this casino is rigged".
   For a product whose entire pitch is trustlessness, this is the worst possible failure.

2. **The UI currently asserts the false claim.** `ShuffleProof.svelte:322` states: "Given
   the revealed seed, anyone can independently verify the entire shuffle sequence."

3. **The "verification" in the UI is the house checking its own homework.**
   `ShuffleProof.svelte:73` calls `tableActor.verify_shuffle(proof.seed_hash,
   revealedSeed)`. That is a query on the *table canister itself*, and all it does is
   recompute a SHA-256 (`lib.rs:4456`). The badge reads "Cryptographically verified
   shuffle", but the only thing verified is that the canister can hash, and the verifier is
   the party the player is supposed to distrust. A real verifier must run on the player's
   machine and must reproduce the *cards*, not the hash.

4. **The new golden vectors pin the wrong behaviour.** `src/poker_core/tests/golden_vectors.txt`
   was generated by running the original engine **natively**, so its 2000 shuffle vectors
   encode the 64-bit shuffle that has never run in production. Any refactor validated
   against them "preserves" behaviour the canister never had. This must be fixed before the
   vectors are trusted: either generate them from a wasm32 execution, or make the shuffle
   platform-independent and regenerate.

## Fairness is not affected

The truncation discards 32 bits of a 64-bit value before a modulo by at most 52. The
residual modulo bias is on the order of 52/2³², i.e. about one part in eighty million, and
it applies identically to every seat. Nobody gains an edge. The defect is verifiability and
cross-platform determinism, not randomness quality.

## The fix

Nobody has ever played on mainnet, so there is no deck history to preserve and the shuffle
can simply be made correct.

1. **Make the arithmetic explicitly width-independent.** Never route a random value through
   `usize`:

   ```rust
   let j = (random_value % (i as u64 + 1)) as usize;
   ```

2. **Remove the modulo bias while we are here**, so the algorithm is defensible rather than
   merely deterministic: draw and reject. Take the next 8 bytes of the hash chain, reject
   values in the final partial bucket, and re-hash on rejection. Document the exact
   procedure, including the rejection rule, because a verifier has to reproduce it bit for
   bit.

3. **Pin it with vectors produced by wasm32, not by the host.** Add a test that runs the
   shuffle under a wasm runtime (or under PocketIC against the real canister) and asserts
   the same vectors the native test asserts. A native-only golden test cannot catch this
   class of bug, which is precisely how it survived.

4. **Ship a real client-side verifier.** Reproduce the deck in the browser, in JavaScript,
   from the revealed seed, and show the player their own two cards and the board being
   re-derived. Stop calling `verify_shuffle` on the canister for anything a player is meant
   to trust. This is also the single biggest trust differentiator available: no major poker
   client can offer it, because none of them can publish the shuffle.

5. **Add a `wasm32` unit-test job to CI.** Any pure-logic function whose result feeds the
   deal or the money must be tested on the target that actually runs it.
